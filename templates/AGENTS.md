## 1. レイヤー分離（厳守）

```
bundle-root/
├── MAP.md             ← 経路表。**最初に読む**。層ではない
├── SYSTEMMAP.md       ← システムの全体像と拡張のしかた。層ではない
├── human.md           ← 利用者について。層ではない
├── Task.md            ← 未完了と直近の完了。層ではない
├── raw/               ← Layer 1: 人間の受信箱。原本を置く。AI は書き込めない
├── wiki/              ← Layer 2: 正典。人間・AI が読み書きする
│   ├── 1-projects/    ← PARA: 進行中（終わりがある）
│   ├── 2-areas/       ← PARA: 期日はないが優先したい関心
│   ├── 3-resources/   ← PARA: 役立つ知識（既定）
│   ├── 4-archive/     ← PARA: 現在使っていない
│   ├── AGENTS.md      ← この規約
│   ├── skills/        ← SkillSpace: <カテゴリ>/<スキル名>/SKILL.md
│   ├── loops/         ← ループ設計と実行履歴。1 設計 = 1 ファイル
│   ├── knowhow/       ← ノウハウ: エージェントが残す短い学び（type: Knowhow）
│   ├── activity/      ← 保存した活動サマリ（type: ActivitySummary）
│   ├── bases/         ← 一覧・集計ビュー .base（概念ではない）
│   ├── graph/         ← 知識グラフの設計: schema.md（型 GraphSchema）と canvases/（.canvas）
│   ├── index.md       ← 予約ファイル（frontmatter なし）
│   └── log.md         ← 予約ファイル（日付グループ・新しい順）
└── .rag/              ← Layer 3: 派生インデックス。再構築可能。手編集しない
```

**層は 3 つだけです。**

- `MAP.md`・`SYSTEMMAP.md`・`human.md`・`Task.md` は**層の外**、バンドル直下にあります。
  3 層は同じ素材の 3 つの段階（原本 → 正典 → 派生）ですが、この 3 つは
  その素材ではありません。置き場所の説明・人・進行中の作業であって、
  知識でも知識の派生物でもないからです。
- `AGENTS.md`・`skills/`・`loops/` は wiki 層の中身です。いずれも
  「ウィキについて」の整理済みコンテンツだからです。

- **raw/ は人間の受信箱です。** 人間が原本を置き、Notion や Google ドライブからの
  取り込みもここに入ります。**エージェントは書き込めません。**
  raw/ は「実際に受け取ったもの」の記録であり、エージェントが生成したものは
  どこからも受け取っていないためです。
  引き上げが必要なら「この資料を wiki に上げてください」とユーザーに依頼してください。
- **wiki/ と .rag/ は人間・エージェントの双方が読み書きできます。**
  `move_file` での整理も自由です。
- **wiki/** 配下の概念ファイルは OKF v0.2 準拠。
- **.rag/** はアプリまたは `rebuild_rag` ツールが管理する。
- **wiki/skills/** は知識ではなく**手順**。概念として索引されないので `search` では
  出てこない。代わりに `skill_find` を使う。
  構成は `skills/<カテゴリ>/<スキル名>/SKILL.md`。**参照は常にスキル名だけ**で行う
  （カテゴリを変えても参照が壊れないため）。
  `para: archive` のスキルは提案されないが、名前を指定すれば開ける。
- **wiki/loops/** は知識ではなく**作業の型と履歴**。これも索引対象外。`loop_list` で見る。
- **wiki/knowhow/** と **wiki/activity/** は**ふつうの概念**です。索引され、`search` で出てきます
  （使い方は §4 の「ノウハウ」「活動サマリ」）。
- **wiki/AGENTS.md**（この文書）も概念ではない。

### PARA — 優先度の順序

wiki/ の概念は 4 つのフォルダのいずれかに入ります。**これは優先順位です。**

| 順 | フォルダ | 意味 |
|----|---------|------|
| 1 | `1-projects/` | 現在進行中で、終わりのあるもの |
| 2 | `2-areas/` | 期日はないが、優先したい関心ごと |
| 3 | `3-resources/` | 役に立つ知識。必要なときに参照する（**既定**） |
| 4 | `4-archive/` | 現在使っていないもの。記録として残す |

- **検索と取得はこの順で重み付けされます。** 同じくらい一致する 2 件があれば、
  進行中のプロジェクトが先に、アーカイブが最後に出ます。
- **アーカイブは削除ではありません。** 検索から消えるのではなく、順位が大きく
  下がるだけです。唯一の答えであれば今でも見つかります。
- 分類を変えるときは `set_para` を使ってください。**実際にファイルを移動し、
  被リンクも書き換えます。**
- どこにも入っていない概念は `3-resources/` 扱いです。

**使わなくなったものは削除ではなくアーカイブへ。** 何が現役かを
`list_para` で確かめてから作業を始めてください。

### ライフサイクル — `Product` と `DEAD`

PARA が「どれだけ現役か」を表すのに対し、ライフサイクルは**状態の種類**を表します。
frontmatter の `tags` に付ける印で、`set_lifecycle` で付け外しします
（`product` / `dead` / `none`。表記は `Product` / `DEAD` に揃えて書かれます）。
**両方が同時に付くことはありません。** 片方を付けるともう片方は外れます。

- **`Product` を付けるのは、完成して信頼してよい成果物**（確定した仕様、最終版の回答、
  出荷済みのもの）だけです。下書き (`status: draft`) や途中経過には付けません。
  検索順位がわずかに上がります（PARA の 1 段より小さい補正）。
  人間が確認した、または Supervisor が検証したものを目安にしてください。
- **`DEAD` は削除ではありません。** 役目を終えた・間違っていた・置き換えられた概念に付けると、
  ファイルもリンクも履歴もそのまま残りますが、`search` / `retrieve` / `context_pack` の
  結果には**既定で出なくなります**。古い情報が文脈に紛れ込むのを防ぐための印です。
  `list_concepts` は在庫一覧なので DEAD も載せ、各行に `lifecycle` を付けます。
- **DEAD のファイルを探すには:** `search` に `tags: ["DEAD"]` と `include_dead: true` を渡す。
  過去の判断を調べたいときは `include_dead: true` を付けて検索・取得できます。
- 迷ったら: もう使わないが記録は残したい → `4-archive/`（順位が下がるだけで出る）、
  誤り・置き換え済みで**文脈に出したくない** → `DEAD`。

## 2. OKF v0.2 ルール

### 必須

- すべての概念 `.md`（`index.md` / `log.md` 以外）は YAML frontmatter を持つ。
- frontmatter に **`type`** が必須（空文字不可）。
- 関係は標準 Markdown リンクで表現する（`[label](path.md)`）。

### 推奨 frontmatter

```yaml
---
type: Concept          # 必須。例: Concept, Entity, Summary, Playbook, Note
title: 表示名
description: 一行要約
tags: [tag1, tag2]
generated:
  by: process:claude-code   # または human:name / agent/1.0
  at: 2026-07-31T12:00:00Z
status: stable              # draft | stable | deprecated
---
```

### 予約ファイル

- `index.md` — ディレクトリ一覧。frontmatter なし（ルートのみ `okf_version` 可）。
- `log.md` — 更新履歴。`## YYYY-MM-DD` 日付グループ、**新しい順**、散文の箇条書き（OKF §9）。

## 3. デイリーノートとタスク（規則）

`wiki/daily/YYYY-MM-DD.md` はその日の書き留め場所です。`daily_note` で開き、
無ければ雛形から作られます。ふつうの概念として索引されるので、後から
「先週の火曜に何を決めたか」を `search` で引けます。

### 規則: デイリーノートにタスク要件が書かれていたら Task.md に入れる

**デイリーノートを読んで、`## タスク` の下に未チェックの項目があったら、
`collect_daily_tasks` を呼んでください。**

```
## タスク

- [ ] 議事録を wiki に取り込む        ← 未チェック = 取り込み対象
- [x] 資料を集める → T-0011           ← 済み。二度と取り込まれない
```

呼ぶと、未チェックの各項目が `Task.md` に追加され、ノート側の行は
`[x]` と付与された ID に書き換わります。

**なぜ必要か:** その日のノートに書いた要件は、翌日には誰も見ません。
実際に読まれるのは `Task.md` の方です。書いた場所と読まれる場所が
違うので、移し替えないと要件は消えます。

**注意点:**

- 対象は `## タスク` 見出しの下だけです。ノート内の他のチェックリスト
  （持ち物、手順の確認など）は取り込みません。
- **二重登録されません。** チェック済みの行は対象外なので、同じ日に
  何度呼んでも増えません。
- 取り込んだタスクには「YYYY-MM-DD のノートから」と出所が入ります。
- ユーザーが口頭で依頼した作業は、ノートを経由せず `add_task` で直接
  入れてください。この規則はノートに**書かれた**ものについてです。

## 4. エージェント操作

MCP ツール（典型的な順序）:

1. `read_agents_md` — **必ず最初**
2. `context_pack` — **まとまった作業を始めるとき。** タスクに必要な最小限の
   ファイル群と合致するスキル・ノウハウを、文字数予算内でまとめて返す。1 ファイルずつ
   読み回るより先にこれを呼ぶ。読む範囲は `para_depth`（1=プロジェクトのみ … 4=すべて）で
   絞り、`link_depth`（0〜2）で取得したファイルからのリンク先を一行説明だけ足せる
   （`retrieve` も同じ）
3. `loop_start` — **バンドルを変更するなら必ずこれ。** 現状・スキル・完了条件を返す
4. `skill_open` — `loop_start` が挙げたスキルの手順を読む
5. `retrieve` — **質問に答えるとき。** 見出し単位の本文を引用付きで返す
6. `search` — **ページを探すとき。** 1 ドキュメント 1 件で場所を示す
7. `read_file` — 該当ページ全体を読む（frontmatter・リンク・バックリンク付き）
8. `create_concept` — 新規ページ（frontmatter を自動生成するので非準拠にならない）
9. `write_file` — 既存ページの更新。書き込みと同時に OKF 準拠が検査され、
   `generated` が無いと警告が返る
10. `loop_end` — **最後に必ずこれ。** 変化を突き合わせて記録を閉じる
11. `audit_changes` — 誰（human / どのモデル）が何を変えたかを log.md から一覧する
12. `summarize_activity` — 同じ log.md を、日付と対象パスを添えた読み物にまとめる
    （`save: true` で `wiki/activity/` に保存）
13. `knowhow_find` / `knowhow_add` — 作業前に過去の学びを引き、非自明な発見の後に残す
    （下の「ノウハウ」）
14. `base_list` / `base_query` / `base_write` — 一覧・件数・集計はベースに聞く
    （下の「ベース」）
15. `canvas_list` / `canvas_read` / `canvas_from_links` / `canvas_write` / `graph_schema` —
    概念の関係を図で読む・描く、型と関係の種類を知る（下の「関係図」「型付き関係とスキーマ」）
16. `system_map` — SYSTEMMAP.md を読む・更新する（下の「SYSTEMMAP」）
17. `rebuild_index` / `rebuild_rag` — 必要時のみ

### ノウハウ — エージェント間で学びを渡す

ノウハウは「踏んだ罠」「この方法で上手くいった」「このバンドルの流儀」のような
**短い学び 1 件**です。手順書（スキル）ほど重くなく、別のエージェント
（Claude Code・Codex など）が次の作業で同じ失敗をしないために残します。
`wiki/knowhow/` に `type: Knowhow` の概念として保存され、`by` に記録した
エージェントの ID が入ります。

- **作業を始める前に確認する。** `context_pack` は一致する上位 3 件を自動で添えます。
  使わない場合は `knowhow_find` を呼んでください（題名・説明・スコア・記録者だけを返す安価な呼び出し）。
  関係しそうなものは `read_file` で本文を読みます。
- **非自明な発見をしたら、作業の最後に `knowhow_add` で 1 件残す。**
  対象は、調べないと分からなかったこと・一度失敗してから分かったこと・次も効く流儀です。
  当たり前のこと、この会話だけで意味が通じるメモ、長い手順（→ スキルにする）は残しません。
- **出所を必ず付ける。** `actor` に自分の ID（`process:claude-code` / `process:codex` など）を渡す。
  推測は書かない。確かめたことだけを、最初の 1 行に結論を置いて書く。
- 間違いと分かった・古くなったノウハウは削除せず `set_lifecycle` で `dead` にする。
  以後の `knowhow_find` と `context_pack` には出なくなります。

### ベース — 一覧と集計は、ファイルを読み回さず問い合わせる

ベース（`.base`）は「概念に対する保存済みの一覧・集計ビュー」です。形式は
Obsidian Bases と同じ YAML なので、Obsidian でも開けます。`wiki/` のどこにでも置け、
概念ではないので検索インデックスにも入りません。`wiki/bases/` に例があります。

- **一覧や件数を知りたいときは、多数のファイルを開く前に `base_list` を見る。**
  合うベースがあれば `base_query { path, view?, limit? }` が行・グループ・集計を
  JSON と Markdown の表で返します（行は 500 件まで）。
- **同じ問い（例: PARA ごとの Product 一覧）を二度以上聞きそうなら `base_write` でベースを作る。**
  YAML と対応範囲を検証してから、渡した文面のまま保存します。書けるのは
  `filters`（`file.hasTag` / `file.inFolder` / `file.hasLink` / プロパティ比較）、`formulas`、
  `properties`（`displayName`）、`views`（`table` と `cards`。`order` / `sort` / `limit` /
  `groupBy` / `summaries`）です。`file.para`（project など）も使えます。
- 未対応の項目（`file.size` など）は空として扱われ、`base_query` の `warnings` に出ます。
  知らないキーは消さずにそのまま残してください。

### 関係図（キャンバス）— 関係は図で読む

キャンバス（`.canvas`）は概念の関係図です。形式は JSON Canvas 1.0 で、Obsidian でもそのまま
開けます。`wiki/` のどこにでも置け（既定は `wiki/graph/canvases/`）、概念ではないので
検索インデックスにも入りません。

- **関係をたどる前に `canvas_list` を見る。** 合う図があれば `canvas_read { path }` が
  構造（JSON）と、グループ別・エッジのラベル付きの短いアウトラインを返します。
  ファイルノードは概念のタイトルと説明に解決されます。
- **ある概念の周辺を知りたいときは `canvas_from_links { root | query, depth?, path }`。**
  リンクと型付き関係をたどって図を作り、保存します（`depth` は 0〜3。位置は決定的で、
  同じ入力なら同じファイルになります）。普通のリンクにはラベルがなく、型付き関係には
  種類（`depends_on` など）が付きます。同じパスに既に図があるときは上書きせずエラーに
  なります（置き換えるなら `overwrite: true`）。
- 手書きするなら `canvas_write { path, content }`。仕様と大きさの上限（1 MiB・ノード 2000・
  エッジ 5000）を検証してから渡した文面のまま保存するので、知らないキーや並び順は
  Obsidian との往復で保たれます。ファイルノードの `file` はバンドルからの相対パス
  （`wiki/3-resources/foo.md`）で書きます。

### 型付き関係とスキーマ — 関係に種類を付ける

概念は frontmatter に型付き関係を書けます。パスでも `[[リンク]]` でもかまいません。

```yaml
relations:
  depends_on: [3-resources/a, "[[b]]"]
  part_of: wiki/1-projects/p.md
```

- 本文のリンクと同じく**リンクとして数えられます**（バックリンク、`unresolved_links`、
  `link_depth`）。`unresolved_links` は関係の行に `relation` を付けて返します。
- `wiki/graph/schema.md`（型 `GraphSchema`）が、このバンドルで使う概念の `types` と
  関係の `kinds`（名前・説明・任意で `from` / `to` の型）を宣言します。`graph_schema` で
  読めます。
- **宣言にない型・関係の種類は `graph_schema` の `warnings` に出ます**（エラーではなく、
  `loop_end` の非準拠にも数えません）。新しい型や種類を使い始めたら、まずスキーマに足して
  ください。スキーマが無いバンドルでは何も警告しません。
- `move_file` / `set_para` は、移動したファイルを指す `relations` の項目も、書かれていた形のまま
  その場で書き換えます（移動したファイル自身の相対パスも直します）。安全に編集できない書き方
  （複数行の `[ ]`、アンカーなど）は触らず、結果に「dangle する関係」として出るので手で直してください。

### SYSTEMMAP — システムの地図

`SYSTEMMAP.md`（バンドル直下、MAP.md の隣）は、層・フォルダ・ツールの群・ベース／キャンバス／
スキル／ループ／ノウハウ／グラフの置き場所と、**拡張のしかた**（型・関係の種類・ベース・
キャンバス・スキル・ループ・MCP ツールを足す手順）を説明します。マーカーの間は自動生成で、
現在の件数と一覧が入ります。

- 構造を変える前に `system_map` で読む。
- **型・関係の種類・ベース・キャンバス・スキル・ループを足したら `system_map { refresh: true }`。**
  マーカーの間だけが書き換わり、外の文章は 1 バイトも変わりません。SYSTEMMAP.md が無い
  バンドルは、最初の refresh で作られます。開始マーカーと終了マーカーが 1 組ちょうど無い
  ファイル（片方だけ、逆順、重複）は書き換えず、どちらを戻すかをエラーで返します。

### 活動サマリ — 何があったかを辿れる形で

`summarize_activity` は log.md の行だけから、エージェント別・ファイル別にまとめた
ページを作ります。各行に**ログの日付と対象パス**が付くので、書かれていることは
すべて元の行に遡れます（推測は含まれません）。引き継ぎや週次の振り返りに使い、
残したいときは `save: true` で `wiki/activity/<since>_<until>[_<actor>].md` に保存します。

### ループ（作業の前後で確認する）

**バンドルを変更する作業は、必ず `loop_start` で始め `loop_end` で終えること。**

```
loop_list                 ← 使えるループ設計を見る（再開時はまずこれ）
   ↓
loop_start(name)          ← 現状を記録し、スキルと完了条件を返す
   ↓  skill_open → 作業（write_file / create_concept …）
   ↓  ファイル変更は自動で記録される
loop_end(outcome)         ← 変化を突き合わせ、完了条件を返す
```

#### 原則: 1 つのループ設計 = 1 ファイル

「ループ」は**繰り返し使う作業の型**です（例: 議事録取り込み、週次点検）。

- 1 つの設計につきファイルは 1 つ。**実行するたびにファイルは増えません。**
  同じ設計の実行履歴は、その 1 ファイルの中に積み上がります。
- 別々の設計が同じファイルを共有することはありません。
- **同時に実行できるのは 1 つだけ。** 実行中に別のループを始めようとすると
  拒否されます。先に `loop_end` を呼んでください。
- 履歴は上限付きです。直近数回は詳細、それ以前は 1 行、さらに古いものは
  件数だけになります。読めない記録は記録ではないためです。

**なぜこの形か:** 実行ごとにファイルを作ると、同じ作業の記録が何百件にもなり、
容量も可読性も破綻します。設計単位なら、その作業が前回どうだったかを 1 ファイル
見るだけで分かります。

#### 作業前に確認すること

`loop_start` の戻り値がそのままチェックリストです。

| 項目 | 見るところ | 判断 |
|------|-----------|------|
| 手順 | `skill` / `suggested` | `skill_open` で読む |
| 完了条件 | `checks` | 終了時に満たすべきこと |
| 現状 | `before` | 既に非準拠があるなら自分のせいにしない |
| 前回 | `lastRun` | 前回の結果・残課題を踏まえる |

#### 作業後に確認すること

`loop_end` が開始時と突き合わせて返します。

- **`OKF 非準拠` が増えていたらエラーになります。** 直してから報告すること。
  「閉じたから終わり」ではありません。
- `未解決リンク` の増加は**正常**です。書くべきページを見つけた証拠。
- 返ってきた**完了条件を 1 つずつ確認**して、結果に書くこと。
- 完了できなかったときは `status: "abandoned"` で閉じる。開いたままにしない。

#### 新しいループ設計を作る

繰り返す作業だと分かったら `loop_define` で型にしてください。
一度きりの作業なら、`loop_start` に `goal` を渡せばその場で作られます。

## 5. 長時間自律作業とモデル階層

### 長時間自律作業プロトコル

セッションをまたぐ・複数段階に及ぶ作業では:

1. **開始時** — `read_map` → `list_tasks` → `read_human` の順で状況を掴み、
   まとまった作業なら `context_pack` で必要な文脈を一度に取る
2. **実行中** — 大きな仕事は必ず `loop_define` / `loop_start` で型にする。
   ファイル変更は自動で記録されるが、**判断・却下した案・見つけた矛盾**は
   `loop_note` で残す。それ以外に痕跡が残らないため
3. **完了時** — `update_task` で Task.md を最新にし、`loop_end` で閉じる。
   途中で終わるときも `status: "abandoned"` で閉じ、残課題を outcome に書く。
   非自明な発見があれば `knowhow_add` で 1 件残す（出所付き）
4. **推測で書かない。** 根拠のない記述は書かないか、`status: draft` を付けて
   下書きであることを明示する

### モデル階層（Supervisor / Worker）

複数のモデル（フロンティア + ローカル LLM）が同じバンドルで働く前提の役割分担です。
どのモデルにもこの規約と同じ層ルール・記録・検査がかかります。

| Tier | 役割 | 想定 |
|------|------|------|
| Supervisor | 計画・分解・検証・`status: stable` への昇格・重要な書き込み | フロンティアモデル |
| Worker | 与えられた文脈内での読み取り・要約・下書き | ローカル LLM など安価なモデル |

- 文脈は `context_pack` で取る。Worker は `tier: "worker"`（小さいパック）、
  Supervisor は `tier: "supervisor"`（広いパック）を指定する
- **Worker の書き込みは `status: draft` まで。** `stable` への昇格と内容の検証は
  Supervisor か人間が行う。Worker は渡されたパックの外を大きく書き換えない
- すべての書き込みに `generated.by` を付ける（`process:<モデル名>` / `human:<名前>`）。
  `create_concept` は自動で付け、`write_file` は無いと警告を返す
- レビュー時は `audit_changes` で「どのモデルが・いつ・何を変えたか」を確認してから
  信頼する

## 6. 命名とリンク

- ファイル名: kebab-case、小文字、ASCII 推奨
- 概念 ID = **wiki 層からの相対パス**から `.md` を除いたもの
  （`wiki/topics/foo.md` → `topics/foo`）
- リンクは標準 Markdown `[label](path.md)` が正式形式。
  `[[topics/foo]]` / `[[foo|表示名]]` も同じ ID 空間に解決される。
- `[[foo]]` のような単独名は、その名前のページが**一意なときだけ**解決される。
  曖昧な場合は解決されないので、パスを明示すること。
