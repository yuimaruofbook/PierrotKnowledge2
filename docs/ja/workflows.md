## 1. 基本サイクル

```
   ┌─────────────────────────────────────────┐
   │                                         │
   ▼                                         │
 資料を raw/ に置く                          │
   │                                         │
   ▼                                         │
 Ingest ── エージェントが読んで wiki/ に概念化
   │                                         │
   ▼                                         │
 Query ─── retrieve で質問に答える           │
   │                                         │
   ▼                                         │
 Lint ──── 未解決リンク・非準拠を解消 ───────┘
           （欠落が次の ingest を導く）
```

**複利が効くのはこのループが回るとき**です。回答を書き戻し、未解決リンクを埋め、そのたびに次の質問がより早く・より正確に答えられるようになります。

## 2. 資料を取り込む（Ingest）

### 手順

1. 元資料を `raw/` に置きます（PDF・議事録・エクスポート・書き起こしなど）。
2. エージェントに取り込みを指示します。
3. `rebuild_index` で `index.md` を更新します。

手順 1 は、ファイルを直接置くほかに 2 通りあります。

- **他のツールからコピーして貼り付ける** — Notion や Google ドキュメントから貼ると、書式を保ったまま Markdown になります。
- **MCP で直接つなぐ** — ツールバーの「接続」から Notion・GitHub・Google Drive などを呼び、結果を `raw/` に取り込みます。取得元と引数が自動で記録されるため、出典を手で書く必要がありません。

どちらも [使い方ガイド](./usage.md#10-外部サービスから取り込む) を参照してください。**いずれの経路でも `raw/` に入るところまでが取り込みです。** そこから先の整理は変わりません。

### エージェントへの指示例

```
raw/2026-q3-review.md を読んで、wiki に取り込んでください。

手順:
1. read_agents_md でこのバンドルの規約を確認
2. search で既存の関連ページを探す（重複を作らない）
3. 新しい概念は create_concept で作成
4. 既存ページに追記すべき内容は write_file で更新
5. 関連ページ同士を [[wikilink]] で相互参照
6. 最後に rebuild_index

原則:
- raw/ は絶対に書き換えない
- 1つの資料が複数ページに触れてよい（10ページでも構わない）
- 出典を frontmatter の sources に残す
- まだ書いていない概念には [[リンク]] を張っておく（後で埋める）
```

最後の指示が重要です。**未解決リンクは欠落知識の可視化**であり、次の取り込みの計画になります。

### 出典を残す

```yaml
---
type: Summary
title: 2026年Q3 レビュー要点
sources:
  - id: q3-review
    resource: /raw/2026-q3-review.md
    title: Q3 レビュー議事録
    last_modified: 2026-07-15
generated:
  by: process:claude-code
  at: 2026-08-01T10:00:00Z
---
```

こうしておくと、後から「この主張はどこから来たのか」を辿れます。

### 1 資料 = 1 ページにしない

gist の言葉どおり «A single source might touch 10-15 wiki pages»。資料ごとにページを作るのは**ファイルの置き換えであって知識化ではありません**。エンティティ・概念・決定事項の単位で切り出してください。

## 3. 質問して答えさせる（Query）

### `retrieve` と `search` の使い分け

| 目的 | ツール | 返るもの |
|------|--------|---------|
| 「X とは何か」に答える | **`retrieve`** | 見出し単位の本文＋引用アンカー＋文字数予算 |
| 「X はどのページか」を探す | **`search`** | ページごとに 1 件、該当セクション名付き |

エージェントへの指示例:

```
このナレッジベースを参照して答えてください。
まず read_agents_md、次に retrieve を使うこと。
回答には必ず anchor（例 topics/foo.md#見出し）を引用してください。
```

### 絞り込み

```
retrieve("認証はどう実装している？", type="Playbook", tags=["security"])
retrieve("設計の経緯", path_prefix="wiki/decisions/")
```

### 予算の調整

```
retrieve("全体像を教えて", limit=15, budget_chars=12000)
retrieve("一行で", limit=2, budget_chars=800)
```

既定は 8 パッセージ・6000 文字です。文字数指定なのは、トークン数がモデル依存であり、**曖昧さを正直に表現するため**です。

### 良い回答は書き戻す

これが複利の本体です。

```
今の回答を wiki/topics/auth-overview.md として保存してください。
type は Summary、参照した各ページに [[リンク]] を張ってください。
```

次に同じ質問が来たとき、統合済みのページが 1 回で返ります。

## 4. 健全性を保つ（Lint）

週次・月次で回すことを想定した点検です。

### エージェントに任せる

```
wiki の健全性を点検してください。

1. check_conformance — OKF 違反があれば修正（frontmatter・type の欠落）
2. unresolved_links — 未作成ページを一覧し、書くべきものを提案
3. list_concepts — 孤立ページ（backlinks が空）を探す
4. 内容の矛盾があれば指摘（ページを削除せず、本文で明示してリンク）

矛盾を見つけたら、勝手にどちらかを消さないこと。
両論を残し、status: deprecated を使うか、本文で経緯を説明してください。
```

### UI で確認する

| 確認 | 場所 |
|------|------|
| 非準拠の件数 | ステータスバー右 |
| 非準拠の一覧 | `Ctrl+Shift+P` → OKF 準拠チェック |
| 未解決リンク | ツールバーのバッジ、または `Ctrl+Shift+P` |

### 陳腐化の管理

```yaml
stale_after: 2026-12-31
```

期限を過ぎた概念は「陳腐化」とみなされます。相対 TTL ではなく絶対日付なので、いつ読んでも判定が変わりません。

## 5. AGENTS.md を育てる

> **「スキーマこそが本当のプロダクトである」**

`AGENTS.md` は単なる説明書ではなく、**知識ベースの運用ルールそのもの**です。使いながら育ててください。

書くべきこと:

- このバンドルのドメインは何か
- どんな `type` を使うか、それぞれ何を意味するか
- ディレクトリ構成の規約（`decisions/`・`entities/`・`topics/` など）
- 取り込み手順（どこまで細かく分割するか）
- 矛盾が見つかったときの扱い
- 品質基準（出典必須か、`verified` を求めるか）

テンプレートは `templates/AGENTS.md` にあります。バンドルを作ると自動でコピーされます。

エージェントが毎回最初に読むので、**ここを直せば全エージェントの振る舞いが変わります**。

## 6. `type` の設計

OKF は値を規定しません。小さく始めるのが実際的です。

### 出発点

| type | 用途 |
|------|------|
| `Note` | 雑多なメモ。分類前の置き場 |
| `Concept` | 概念・用語の定義 |

### 育ったあと

| type | 用途 |
|------|------|
| `Entity` | 人・組織・製品・システムなど固有の対象 |
| `Summary` | 複数資料を統合した要約 |
| `Playbook` | 手順書・運用方法 |
| `Decision` | 意思決定の記録（ADR 的） |
| `Question` | 未解決の問い |

`Question` 型は有効です。**答えの無い問いを一級市民として置く**と、知識の欠落が可視化されます。

現在使われている型は `list_tags` で確認できます。

---

## 7. タグの設計

`type` が「これは何か」なら、タグは「どの文脈か」です。

- **少なく保つ。** タグが 50 個あると、どれも意味を持ちません
- **直交させる。** `type: Playbook` + `tags: [security]` のように、型と重複させない
- サイドバーのタグチップで検索を絞り込めます

## 8. 用途別レシピ

### 技術ドキュメント

```
raw/          仕様書・RFC・API ドキュメント
wiki/
  concepts/   ドメイン用語
  systems/    各コンポーネント（type: Entity）
  decisions/  設計判断（type: Decision）
  playbooks/  運用手順（type: Playbook）
```

**効きどころ**: 「なぜこうなっているのか」を `Decision` で残すと、半年後の自分とエージェントの両方が救われます。

### 研究・調査ノート

```
raw/          論文 PDF・書き起こし・実験ログ
wiki/
  papers/     論文ごとの要約（type: Summary、sources 必須）
  concepts/   手法・概念（type: Concept）
  questions/  未解決の問い（type: Question）
```

**効きどころ**: `sources` を必ず埋め、`verified` で人間の確認を記録します。信頼ティアが `human-reviewed` になります。

### 議事録・意思決定の蓄積

```
raw/          生の議事録
wiki/
  decisions/  決定事項（type: Decision、stale_after で見直し期限）
  people/     関係者（type: Entity）
  topics/     継続的な論点
```

**効きどころ**: 決定には `stale_after` を入れて、定期的な見直しを強制します。

### コードベースの知識

```
raw/          設計メモ・障害報告
wiki/
  modules/    モジュールごとの責務（type: Entity）
  patterns/   コーディング規約（type: Playbook）
  incidents/  障害と対応（type: Summary）
```

**効きどころ**: このバンドルをコーディングエージェントの MCP に繋ぐと、コードを読む前に設計意図を参照できます。

### 個人の Zettelkasten

```
wiki/          （raw/ は使わなくてもよい）
  *.md         フラットに置き、[[リンク]]で繋ぐ
```

**効きどころ**: `wiki/` を作らず、フォルダ直下に置いてもそのまま開けます。未解決リンクを積極的に作り、あとで埋めていく運用が向いています。

## 9. チームで使う

**git で共有します。** ノートは Markdown なので、差分・レビュー・履歴がそのまま使えます。

推奨する `.gitignore`:

```gitignore
.rag/        # 派生物。各自の環境で再構築される
```

`raw/` を含めるかは資料の性質次第です。大きなバイナリなら Git LFS か、リポジトリ外に置いて `resource` で参照します。

### コンフリクトへの耐性

- `wiki/**/*.md` — 通常の Markdown 差分。マージしやすい
- `wiki/index.md` — 生成物。衝突したらどちらかを取って「再構築」
- `wiki/log.md` — **新しい順**のため先頭で衝突しやすい。両方を残してマージするのが安全

### Actor を使い分ける

```
人間の編集     → human:<名前>
CI/自動処理    → process:<名前>
エージェント   → process:claude-code など
```

誰が書いたかが `log.md` と `generated.by` に残り、信頼ティアの判定にも使われます。

## 10. 規模が大きくなったら

gist は `index.md` 方式の限界を «~100 sources, ~hundreds of pages» としています。本アプリはその先を BM25 インデックスで補いますが、それでも運用上の工夫は要ります。

| 症状 | 対処 |
|------|------|
| `index.md` が長すぎて読めない | サブディレクトリを増やす。OKF はネストした `index.md` を許容（本アプリは自動生成しないが手書き可） |
| 検索結果が多すぎる | `type` / `tags` / `path_prefix` で絞る |
| `retrieve` が的外れ | 質問を具体化する。または `min_content_matches` を上げる |
| 似たページが増えた | 統合して 1 ページにし、古い方は `status: deprecated` にしてリンクを残す |
| 索引が重い | `.rag/` を削除して再構築 |

## 11. アンチパターン

| やりがちなこと | なぜ問題か | 代わりに |
|--------------|-----------|---------|
| `raw/` を直接編集する | 唯一の真実の源が失われる。アプリも拒否する | `wiki/` に書く |
| 資料 1 つ = ページ 1 つ | ファイルの置き換えであって知識化ではない | 概念・エンティティ単位で切る |
| 未解決リンクを消す | 欠落の記録が失われる | 残す。埋めるべき知識のリストとして使う |
| `write_file` + `delete_file` でリネーム | **被リンクが黙って壊れる** | `move_file` を使う（自動追従する） |
| 矛盾したページを片方削除 | 経緯が失われる | 両論を残し `deprecated` とリンクで示す |
| `type` を最初から 20 種類作る | 使い分けられず形骸化する | `Note` / `Concept` から始める |
| `.rag/` を git に入れる | 派生物。衝突源にしかならない | `.gitignore` に入れる |
| エージェントに AGENTS.md を読ませない | 規約が守られず、バンドルが荒れる | 最初に `read_agents_md` を呼ばせる |

## 12. すぐ使える指示テンプレート

### 取り込み

```
raw/<ファイル名> を wiki に取り込んでください。
read_agents_md → search（重複確認）→ create_concept / write_file → rebuild_index の順で。
raw/ は書き換えないこと。未執筆の概念には [[リンク]] を張っておくこと。
```

### 調査

```
「<質問>」について、この知識ベースだけを根拠に答えてください。
retrieve を使い、回答には anchor を引用すること。
根拠が不十分なら「情報が足りない」と言い、何が欠けているか示してください。
```

### 定期点検

```
wiki を点検してください。
check_conformance / unresolved_links / 孤立ページの確認を行い、
修正案を提示してから実行してください。ページの削除は提案のみで、実行しないこと。
```

### 知識の育成

```
unresolved_links を確認し、最も価値の高い未作成ページを3つ選んで、
raw/ の資料を根拠に作成してください。根拠が無いものは作らず、その旨報告してください。
```
