## 1. なぜ必要か

エージェントに手順を教える素朴な方法は、システムプロンプトに全部書くことです。
これは**スキルが増えるほど破綻します**。

| 方式 | 3 スキル | 20 スキル | 問題 |
|------|---------|-----------|------|
| 全文をプロンプトに入れる | ~1,900 tok | ~13,000 tok | 依頼文の居場所が無くなる |
| **SkillSpace** | **~230 tok** | ~1,500 tok | 選ばれた 1 件だけ展開 |

SkillSpace の考え方は単純です。

> **説明は常に読む。手順は選ばれたときだけ読む。**

`description` は「これは何のスキルか」を伝える**ルーティングキー**であって、
要約ではありません。本文は長くて構いません — 開かれたときにしか課金されないからです。

## 2. 3 段階の開示

```
skills/
├── okf-ingest/
│   ├── SKILL.md      ← 段階 2: 選ばれたときだけ読む
│   └── reference.md  ← 段階 3: 本文が指したときだけ読む
├── wiki-answer/
│   └── SKILL.md
└── wiki-lint/
    └── SKILL.md
```

| 段階 | MCP ツール | コスト | 返るもの |
|------|-----------|--------|---------|
| **1** | `skill_find` / `skill_list` | ほぼ無料 | 名前・説明・タグ・**本文の推定トークン数** |
| **2** | `skill_open` | 本文 1 件分 | 選んだスキルの手順 + 補助ファイル名 |
| **3** | `skill_read` | ファイル 1 件分 | 本文が指した補助資料だけ |

段階 1 は**手順本文を一切含みません**。これは設計の中心なので、テストで
明示的に検証しています（`test/skillspace.test.ts`）。

### エージェント側の動き

1. `skill_find` に**ユーザーの依頼文をそのまま**渡す
2. `confidence` が `high` なら 1 位を `skill_open`
3. `low` なら説明を見比べてから選ぶ
4. 該当が無ければ普通に作業する — **無理に開かない**

## 3. スキルの書き方

`skills/<name>/SKILL.md` を作ります。UI の **Skill → ＋ 新しいスキル** でも作れます。

```markdown
---
name: okf-ingest
description: raw/ の資料を wiki/ の概念ページに整理する手順。議事録・エクスポート・書き起こしを取り込むとき。
when: [取り込み, 整理, ingest, 議事録, エクスポート]
tags: [ingest, workflow]
allowed-tools: [read_agents_md, search, create_concept]
---

# 資料を知識にする

（手順をここに）
```

| フィールド | 必須 | 役割 |
|-----------|------|------|
| `name` | ✔ | 識別子。英小文字・数字・ハイフン。フォルダ名と一致させる |
| `description` | ✔ | **常時読まれる唯一の部分。** 400 文字以内 |
| `when` | | 選択用の追加語彙。**description より強く効きます** |
| `tags` | | 分類 |
| `allowed-tools` | | 参考情報。強制はされません（層の規約が唯一の強制です） |

### `description` の書き方

**「何をするか」ではなく「どんなときに使うか」を書いてください。**

| ✗ 悪い例 | ✓ 良い例 |
|---------|---------|
| 取り込み手順です | raw/ の資料を wiki/ に整理する手順。議事録・エクスポート・書き起こしを取り込むとき |
| 検索について | 日本語で検索がヒットしないときの調べ方と直し方 |

エージェントはこの 1 文だけで判断します。状況が書いていなければ選ばれません。

### `when` の使い方

`description` は**読まれるための文**、`when` は**探されるための語**です。

```yaml
description: 日本語で検索がヒットしないときの調べ方。
when: [検索, ヒットしない, 出てこない, バイグラム, search]
```

ユーザーが実際に打ちそうな言葉 — 同義語、英語、製品名 — を入れてください。
`when` の一致は `description` の一致より高く評価されます。

### 補助ファイル

長い参照表や具体例は別ファイルにしてください。

```
skills/okf-ingest/
├── SKILL.md       ← 手順（毎回読まれる部分ではない、が開けば全部読まれる）
└── reference.md   ← 型の設計指針（本文が指したときだけ）
```

`SKILL.md` の末尾で「詳しくは `reference.md`」と書いておけば、
エージェントは必要なときだけ `skill_read` します。

## 4. 選択のしくみ

ローカルで BM25 系のスコアリングを行います。**API 呼び出しは発生しません。**

### 重み

| 対象 | 重み | 理由 |
|------|------|------|
| `name` | 6 | 識別子は最も直接的な一致 |
| `when` | 4 | 依頼文で実際に使われる語 |
| `tags` | 3 | 分類 |
| `description` | 1 | 説明文。読むための文であって探すための語ではない |

さらに、**一致した語の種類が多いほど加点**されます（1 語が 2 回当たるより、
2 語が 1 回ずつ当たる方が強い証拠だからです）。

### 日本語

CJK は**重なり合うバイグラム**に展開されます（全文検索と同じ方式）。

```
「知識ベース」 → 知識, 識ベ, ベー, ース
```

これにより、`知識ベース` が `知識ベースの設計` の中にあってもヒットします。
分かち書きも形態素解析も要りません。

### 一致が無いときは何も返さない

無関係な候補を返すと、エージェントがそれを開いてしまいます。
**間違った `skill_open` は、開かないことより高くつきます。**
そのためスコア 0 の候補は返さず、「見つかりませんでした」と明示します。

### UI で試す

**Skill** タブの入力欄に依頼文を入れると、実際に何が選ばれ、
開くと何トークンかかるかがその場で分かります。トークンは何も消費しません。

## 5. 同梱スキル

新規バンドルには 3 つ入っています。ingest → answer → lint の 1 周をカバーします。

| スキル | いつ選ばれるか |
|--------|--------------|
| `okf-ingest` | 「取り込んで」「整理して」「議事録を…」 |
| `wiki-answer` | 「〜について教えて」「根拠は」「どうなっている」 |
| `wiki-lint` | 「点検して」「準拠しているか確認して」「重複を…」 |

自分のワークフローに合わせて書き換えてください。**同梱スキルは出発点であって
規定ではありません。**

## 6. エージェントを繋ぐ

**接続 → エージェント接続** タブから、設定ファイルに 1 項目だけ追記します。

### MCP ホスト（設定を書けば繋がる）

| ツール | 設定ファイル | 形式 |
|--------|-------------|------|
| **Claude Code** | `<バンドル>/.mcp.json` | `mcpServers` |
| **Codex** | `~/.codex/config.toml` | `[mcp_servers.okf-wiki]` |
| **opencode** | `~/.config/opencode/opencode.json` | `mcp`（`type: "local"` が必要） |
| **Hermes Agent** | `~/.hermes/config.yaml` | `mcp_servers` |

Claude Code だけバンドル内に置きます。プロジェクトスコープなので、
**あなたのグローバル設定に一切触れません。** バンドルのフォルダで `claude` を
起動すれば自動で読まれます。

#### 安全策

- 「**変更内容を見る**」で、書き込む前に全文を確認できます
- 上書き前に必ず `<ファイル>.okf-backup-<時刻>` に退避します
- **既存の設定は消えません。** 1 エントリの追加・置換だけを行います
- Codex の TOML はパースし直さず**テキストとして追記**します
  （コメントやキー順が壊れないようにするためです）

### ローカルモデルサーバー（MCP を話さない）

**Ollama と llama.cpp は MCP クライアントではありません。** モデルサーバーです。
ツール呼び出しは出力できますが、実行する側がありません。

そのため、**本アプリがエージェントループを内蔵**しています（次節）。

## 7. ローカルモデルで動かす

**接続 → ローカル実行** タブです。

```
本アプリ内蔵エージェント
  ├ POST /v1/chat/completions  (Ollama | llama.cpp)
  ├ tools = [skill_find, skill_open, skill_read, retrieve,
  │          search, read_file, list_files, create_concept, write_file]
  └ ループ: 応答 → tool_call → 実行 → 結果を戻す → 再投入
```

### 必要なもの

| | 既定 URL | 注意 |
|---|---------|------|
| **Ollama** | `http://localhost:11434/v1` | **tools 対応モデル**が必要（`ollama show <model>` の capabilities に `tools`） |
| **llama.cpp** | `http://localhost:8080/v1` | `llama-server` を **`--jinja` 付き**で起動すること |

> `--jinja` が無いと llama.cpp はツールを**黙って無視します**。エラーも出ません。

### トークン節約の工夫

ローカルモデルは文脈が狭いので、内蔵ループでは特に切り詰めています。

- **スキルは事前読み込みしない。** `skill_find` を使うよう指示するだけ
- **ツールは 9 個に絞る。** 19 個全部だと小型モデルは依頼文を見失います
- **ツールの説明は 1 文目だけ。** 毎ターン読まれるため
- **ツール結果は 4,000 文字で打ち切る。** 前後を残し中間を省略します
  （引用は末尾にあるので、末尾を切ると出典が消えます）
- **ラウンド上限とトークン予算**で必ず止まります

### 実測

qwen3.5:4b（4.7B・Q4_K_M）で、`skill_find` を自力で呼んで正しいスキルを
選ぶところまで動作を確認しています（`test/agent.test.ts` の live テスト）。

## 8. トークンの実測

同梱 3 スキルでの実測値です。

```
カタログ（常時）      ~230 tok    3 スキル分の名前と説明
okf-ingest  本文      ~674 tok    開いたときだけ
wiki-answer 本文      ~599 tok
wiki-lint   本文      ~642 tok
─────────────────────────────
全部読む場合         ~2,145 tok
SkillSpace（1 件）     ~904 tok    カタログ + 1 本文
削減                     58%
```

スキルが増えるほど差は開きます。20 スキルなら、全文方式が ~13,000 tok なのに対し
SkillSpace は ~1,500 + 選んだ 1 件です。

UI の各スキル行に出る `本文 ~NNN tok` が、その 1 件を開くコストです。

## 9. トラブルシューティング

| 症状 | 原因と対処 |
|------|-----------|
| エージェントがスキルを使わない | `AGENTS.md` を読ませていますか。`read_agents_md` を最初に呼ぶよう指示してください |
| 意図しないスキルが選ばれる | `when` に、ユーザーが実際に使う語を足してください。`description` を変えるより効きます |
| 何も選ばれない | 依頼文の語が `description` にも `when` にも無い状態です。UI の入力欄で試しながら `when` を調整してください |
| スキルが一覧に出ない | `description` が空だと**意図的に除外されます**（選ばれ得ないため）。SKILL.md を確認してください |
| `skill_open` が失敗する | フォルダ名と `name` が一致しているか確認してください |
| llama.cpp がツールを無視する | `--jinja` を付けて `llama-server` を起動してください |
| Ollama が tools を無視する | そのモデルが tools 非対応です。`ollama show <model>` で capabilities を確認してください |
| 接続設定を戻したい | `<ファイル>.okf-backup-<時刻>` を元の名前に戻してください |

## 10. ループ（作業の型）

スキルが「どうやるか」なら、ループは「**いつ始めて、いつ終わったと言えるか**」です。

### 原則: 1 つのループ設計 = 1 ファイル

ループは**繰り返し使う作業の型**です。実行するたびにファイルは増えません。

```
loops/
├── ingest-notes.md    ← 議事録取り込みループ（設計 + 実行履歴）
└── weekly-lint.md     ← 週次点検ループ（設計 + 実行履歴）
```

同じ設計を 100 回実行してもファイルは 1 つで、その中に履歴が積み上がります。
実行ごとにファイルを作る方式だと、同じ作業の記録が何百件にもなり、容量も
可読性も破綻するためです。

この原則は運用ルールではなく**強制**されています。

- 別々の設計が同じファイルを共有することはありません
- 同時に実行できるのは 1 つだけです（実行中に別を始めようとすると拒否されます）
- 設計を編集しても、過去の実行履歴は書き換わりません

### 使い方

| 段階 | ツール | 何が返るか |
|------|--------|-----------|
| 一覧 | `loop_list` | 設計一覧・実行中のもの・前回の結果 |
| 定義 | `loop_define` | 目的・使うスキル・完了条件を登録 |
| 開始 | `loop_start` | **開始時の状態・スキル・完了条件・前回の結果** |
| 記録 | `loop_note` | 判断や気づき（ファイル変更は自動記録） |
| 終了 | `loop_end` | **変化の差分・完了条件・非準拠の警告** |

### 作業前に確認できること

`loop_start` の戻り値がそのままチェックリストになります。

```json
{
  "skill": "okf-ingest",
  "checks": ["重複を search で確認した", "出典を sources に残した"],
  "before": { "concepts": 42, "nonConformant": 0, "unresolvedLinks": 7 },
  "lastRun": { "status": "done", "outcome": "3ページ作成。2件は次回。" },
  "next": "skill_open(\"okf-ingest\") で手順を読んでから作業してください"
}
```

「前回どこまでやったか」が同じ画面にあるので、続きから始められます。

### 作業後に確認できること

`loop_end` が開始時と突き合わせます。

```
- 概念: 42 → 45 (+3)
- OKF 非準拠: 0 → 0 (±0)
- 未解決リンク: 7 → 9 (+2)

完了条件（確認してください）:
- 重複を search で確認した
- 出典を sources に残した
```

- **OKF 非準拠が増えたらエラーになります。** 直してから閉じ直してください
- **未解決リンクの増加は正常です。** 書くべきページを見つけた証拠です

### 履歴の上限

| 範囲 | 残るもの |
|------|---------|
| 直近 5 回 | 経過を含む全記録 |
| それ以前（25 回まで） | 1 行の要約 |
| さらに古いもの | 件数のみ（frontmatter の `runs`） |

31 回実行しても 1 ファイル 3 KB 程度に収まります。

### 同梱ループ

| 設計 | 目的 |
|------|------|
| `ingest-notes` | raw/ の資料を wiki/ に整理する |
| `weekly-lint` | 健全性を点検して直す |

自分の作業に合わせて `loop_define` で追加してください。
