# LLM Wiki パターン

[English](../en/llm-wiki.md) · 日本語

出典: Andrej Karpathy による [LLM Wiki gist](https://gist.github.com/karpathy/442a6bf555914893e9891c11519de94f)（2026年4月公開）

---

## 1. 中心にある主張

> **「RAG は取り出して忘れる。ウィキは蓄積して複利で効く。」**
> （*RAG retrieves and forgets. A wiki accumulates and compounds.*）

通常の RAG では、質問のたびに LLM が生の断片を取り出し、**ゼロから理解をやり直します**。蓄積がありません。gist の言葉では «the LLM is rediscovering knowledge from scratch on every question. There's no accumulation.»

LLM Wiki は順序を入れ替えます。**取り込み時に一度だけ**、LLM が資料を読み、構造を抽出し、矛盾を解消し、相互参照された Markdown 群に書き出します。質問時にはその**コンパイル済みの理解**を読みます。

- 相互参照は**すでにそこにある**
- 統合は**これまで読んだすべてを反映済み**

知識がソフトウェアのように「ビルド」される、という発想です。

## 2. 3 つの層

### Layer 1 — `raw/` （不変・LLM は読み取り専用）

厳選された元資料。**LLM は決して書き換えません。** 唯一の真実の源です。

### Layer 2 — ウィキ（可変・LLM が所有）

LLM が生成した Markdown。要約・エンティティページ・概念ページ・比較など。相互参照は LLM が維持します。ディレクトリ構成はドメインごとに決めます。

### Layer 3 — スキーマ（設定文書）

**`CLAUDE.md` のような設定文書**です。ウィキの構造と規約、取り込み・照会・保守のワークフローを定義します。ウィキと**共進化**します。

gist を拡張した [LLM Wiki v2](https://gist.github.com/rohitg00/2067ab416f7bbe447c1977edaaa681e2) はこう述べます——**「スキーマこそが本当のプロダクトである」**。エンティティ型、関係のルール、取り込み手順、品質基準、矛盾処理のロジックを符号化するからです。

> ### 訂正
>
> 本プロジェクトの以前のドキュメントでは、`.rag/` を「Layer 3」と呼んでいました。**これは誤りです。** 正典の第 3 層は**スキーマ文書**であり、派生インデックスではありません。本ドキュメントで訂正します。
>
> 本アプリにおける正典の第 3 層に当たるのは **`AGENTS.md`** です。`.rag/` は正典に存在しない**追加物**です（[§5](#5-本アプリの実装と差分) 参照）。

## 3. 特別なファイル

### `index.md`

すべてのページを要約とメタデータ付きで列挙する、**内容志向のカタログ**。カテゴリ別に整理し、**取り込みのたびに更新**します。

### `log.md`

**追記専用**の時系列記録。標準的なツールで解析できるよう、一貫した接頭辞を使います。

> **本アプリでの差分**: OKF v0.2 §9 は `log.md` を「`## YYYY-MM-DD` の日付グループ、**新しい順**」と定めており、これは「追記専用」と両立しません。本アプリは **OKF に従います**（新しい項目が上に入る）。両方の仕様に同時に準拠することはできないため、明示的に OKF を優先しました。

## 4. 3 つの操作

| 操作 | 内容 |
|------|------|
| **Ingest**（取り込み） | 新しい資料から要点を抽出し、既存のウィキに統合する。gist いわく「1 つの資料が 10〜15 ページに触れることもある」 |
| **Query**（照会） | ウィキのページを検索し、**引用付きで**回答を統合する。良い回答は新しいページとしてウィキに書き戻せる（複利の源） |
| **Lint**（点検） | 矛盾・陳腐化した主張・孤立ページ・欠落した相互参照を健全性チェックする |

## 5. 本アプリの実装と差分

| 正典 | 本アプリ | 差分の理由 |
|------|---------|-----------|
| `raw/` 不変・LLM 読み取り専用 | `raw/` 同左。**書き込みは技術的に拒否** | 規約ではなく強制にした。解決済み絶対パスで判定するため `./raw/x`・`raw\x`・`wiki/../raw/x` も遮断 |
| ウィキは LLM が所有 | `wiki/` は**人間と AI が対等に読み書き** | 「人間と AI の対称性」を設計原則に据えたため。UI も MCP も同一の書き込み経路を通る |
| スキーマ = `CLAUDE.md` | スキーマ = **`AGENTS.md`** | 特定のエージェント製品に紐づけないため。MCP ツール `read_agents_md` が最初に読ませる |
| （該当なし） | **`.rag/`** — BM25 インデックス | **追加物。** 正典が予告する限界への対応（下記） |
| `log.md` は追記専用 | OKF §9 準拠（新しい順・日付グループ） | 2 つの仕様が衝突するため OKF を優先 |
| `index.md` は自由形式のカタログ | OKF §8 準拠（見出し＋箇条書き） | 同上 |

### なぜ `.rag/` を足したのか

gist 自身がスケール限界を認めています。

> `index.md` による方式は «works surprisingly well at moderate scale (~100 sources, ~hundreds of pages)» ——その先は専用の検索基盤が必要になる。

`.rag/` はその「専用の検索基盤」です。**正典からの逸脱ではなく、正典が想定した先の実装**という位置づけです。

ただし本アプリは埋め込みではなく **BM25（SQLite FTS5）** を選びました。理由:

- モデルも API キーもベクトルストアも不要。ファイル 1 つで完結する
- 厳選済みのウィキが相手なら、キーワード検索で十分な精度が出る
- `.rag/` は削除して再構築できる——**File over App** を壊さない

**正直な限界**: 語彙が重ならない言い換えは検索できません。これは BM25 の性質であり、意味理解ではありません。だからこそ `retrieve` は「見つからない」と言うか、最良の語彙一致を**引用付きで**返してエージェントに判断させます。

### 3 操作の対応

| 正典の操作 | 本アプリでの手段 |
|-----------|----------------|
| **Ingest** | 資料を `raw/` に置く → エージェントが `read_file` で読み `create_concept` で概念化 → `rebuild_index` |
| **Query** | `retrieve`（引用アンカー・文字数予算付き）／ `search`（場所を探す）／ UI の `Ctrl+K` |
| **Lint** | `check_conformance`（OKF 違反）／ `unresolved_links`（欠落知識）／ ステータスバーの非準拠件数 |

## 6. 日本語検索の実装

これは正典にも OKF にも無い、本アプリ固有の対応です。

### 問題

SQLite の `unicode61` トークナイザは**日本語を分かち書きできません**。実測:

| トークナイザ | `軽量`（文中） | `知識` | `ノート` |
|---|---|---|---|
| `unicode61`（素） | **0 件** | 0 件 | **0 件** |
| `trigram` | **0 件**（2文字不可） | **0 件** | 1 件 |

`unicode61` では文全体が 1 トークンになり、`trigram` は 3 文字未満を扱えません。日本語に多い 2 文字語（知識・軽量・設計）が全滅します。

### 解決

**索引時とクエリ時の両方で、CJK を重なり合うバイグラムに展開**します。

```
知識ベース → 「知識」「識ベ」「ベー」「ース」
```

`unicode61` は空白区切りのバイグラムを**字種をまたいでも 1 トークンとして保持**します（`識ベ`・`トア`）。これを実測で確認した上で採用しました。両端が同じ変換を通るため、正確に一致します。

### 2 つの照合モード

| モード | 用途 | 挙動 |
|--------|------|------|
| **phrase** | `search`（場所を探す） | バイグラムの隣接を要求。`知識ベース` が `知識` と `識ベ` の偶然の同居にマッチしない |
| **loose** | `retrieve`（質問に答える） | 全トークンを OR + BM25 でランキング。質問は言い換えであり用語の完全一致ではないため |

loose だけでは無意味な質問にも「それらしい」パッセージが返るため、**内容語 2 語以上の一致**を追加要件にしています。ここでの「内容語」はひらがなのみのバイグラム（はど・どう・てい）を除いたものです。助詞や活用は文書側に存在しないため、それを根拠に数えると長い質問ほど無関係と判定されてしまうからです。

スニペットは SQLite の `snippet()` ではなくアプリ側で生成します。索引側の文字列はバイグラム列であり、そのまま出すと読めないためです。

## 7. このパターンが向く場合・向かない場合

### 向く

- 個人〜小規模チームの知識ベース（gist の目安: 約 100 資料・数百ページ）
- 資料が**安定していて**、統合の価値が繰り返し回収できる
- 「なぜそう決めたか」を残したい設計判断・調査ノート
- 人間もエージェントも同じ知識を参照する運用

### 向かない

- 資料が**高頻度で入れ替わる**（コンパイルのコストを回収できない）
- 大量の非構造データを網羅的に検索したい（従来の RAG のほうが素直）
- 出典そのものを逐語的に引用する必要がある（ウィキは統合済みのため）

### 中間

本アプリは**両方を持つ**構成です。コンパイル済みウィキ（正典の主張）と、その上の BM25 検索（RAG 的な取り出し）を併用します。取り出す対象が生の断片ではなく**厳選済みの節**である点が、素の RAG との違いです。
