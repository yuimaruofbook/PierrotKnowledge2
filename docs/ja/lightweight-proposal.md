# 軽量化の提案

[ベンチマーク結果](../BENCHMARK.md) を踏まえた、メモリ削減の選択肢と推奨です。

> **決着（0.5.0）**: 本書は「メインプロセスの置き換えは割に合わない」と結論しましたが、
> 実際に取った道は**置き換えではなく撤去**でした。ブラウザに配信する `ui` モードが
> 同じ画面を 135 MB で出せると分かり、デスクトップ版に残った固有機能は
> フォルダ選択ダイアログ 1 つだけになったため、それを OS に直接開かせる方式
> （`src/bun/platform.ts`）に置き換えてウィンドウごと削除しました。
> 以下の分析と数値は**当時のまま**残しています。

**先に結論**: メモリの 90% は当プロジェクトのコードではありません。
アプリコードの最適化で得られるのは最大でも約 60 MB です。
本質的な改善には**メインプロセスの置き換え**が必要で、それは割に合わない、
というのが私の推奨です。

---

## 1. 費用の帰属（実測）

追加の切り分け計測を行い、636 MB の全額を帰属させました。

| 構成要素 | ワーキングセット | 割合 | 所有者 |
|----------|----------------:|-----:|--------|
| システム WebView（5 プロセス） | 363 MB | 57% | Microsoft |
| デスクトップシェルのメインプロセス上乗せ | 167 MB | 26% | シェル |
| Bun ランタイムの下限 | 46 MB | 7% | Bun |
| **当アプリのコード + 索引 + 300 ノート** | **61 MB** | **10%** | **私たち** |

### 切り分けの方法

同じ `Workspace` のコードを **デスクトップシェルも WebView も通さず**、
MCP スタンドアロンサーバーとして 300 ノートで起動しました。

```
bun run src/bun/mcp/standalone.ts   →  WS 107.4 MB
素の Bun ランタイム                  →  WS  46.4 MB
                                        ────────────
当アプリのロジック + SQLite 索引      →      61.0 MB
```

デスクトップ版のメインプロセスは同条件で 274 MB。
差の **167 MB がデスクトップシェルの分**です。

### プロセス別（デスクトップ版・300 ノート）

| プロセス | WS |
|----------|---:|
| `bun.exe`（メイン） | 274 MB |
| WebView browser | 119 MB |
| WebView gpu-process | 89 MB |
| WebView renderer | 75 MB |
| WebView utility ×2 | 59 MB |
| WebView crashpad-handler | 21 MB |

## 2. 試して否定された案

### システム WebView のブラウザ引数によるチューニング — **効果なし**

`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` で以下を渡して計測しました。

| 設定 | プロセス数 | 合計 WS | gpu-process |
|------|----------:|--------:|------------:|
| なし（基準） | 7 | 622.7 MB | 88.3 MB |
| `--disable-gpu` | 7 | 580.4 MB | 88.5 MB |
| `--in-process-gpu` | 7 | 612.7 MB | 88.3 MB |

引数が実際に届いていることは、WebView のコマンドラインに
`--disable-gpu` が現れることで確認済みです。それでも
**gpu-process は消えず、プロセス数も変わりません。**
合計 WS の揺れはメインプロセスの GC タイミングによるもので、フラグの効果ではありません。

> **結論**: システム WebView のプロセスモデルはホスト側から実質的に制御できません。
> ここは「設定で削る」対象ではなく、「使うか使わないか」の対象です。

---

## 3. 提案（推奨順）

### 提案 A: ヘッドレス運用を第一級にする 🟢 低コスト・効果大

**実測 107 MB。デスクトップ版の 1/6 です。**

エージェント主体の使い方（Claude Code や Codex から MCP 経由で読み書きする）では、
ウィンドウは不要です。MCP サーバーは既に単体で動きます。

| やること | 工数 |
|----------|------|
| `SETUP.bat -Headless` でサーバーのみ常駐 | 小 |
| タスクトレイ常駐（ウィンドウは必要時のみ生成） | 中 |
| README にヘッドレス時の実測値を明記 | 小 |

**得られるもの**: その用途では **83% 削減**。既存コードで実現可能。

---

### 提案 B: 概念モデルをメモリに常駐させない 🟢 低〜中コスト・将来必須

現在 `Bundle` は**全概念のパース結果をメモリに保持**します。
300 ノートでは 61 MB の一部にすぎませんが、**1 万ノートでは支配的**になります。

| やること | 工数 |
|----------|------|
| frontmatter とリンクのみメモリ、本文は SQLite から都度取得 | 中 |
| LRU で直近参照分だけ保持 | 中 |

**得られるもの**: 300 ノートでは 30〜40 MB 程度。
**1 万ノート規模では桁が変わります。** 現状の数値より、スケール特性のために必要です。

> ベンチマークは 300 ノートまでしか取っていないため、
> **この提案の効果は現時点で未検証**です。まず 1 万ノートで計測すべきです。

---

### 提案 C: アイドル時の解放 🟢 極小コスト・効果は要検証

| やること | 工数 |
|----------|------|
| 起動完了後に `Bun.gc(true)` | 極小 |
| ウィンドウ非アクティブ時に GC + FTS ハンドルを閉じる | 小 |

**得られるもの**: **不明。** JSC の予約分が返るかは実測しないとわかりません。
効果を約束せず、**まず 30 分の実験**として提案します。

---

### 提案 D: デスクトップシェルの 167 MB を調査 🟡 中コスト・効果不確実

ウィンドウ 1 枚と RPC ブリッジに 167 MB は不均衡です。
当プロジェクトは既にシェルにパッチを当てている（three.js / Babylon.js の
先読み除去、6.90 MB → 322 KB）ので、前例はあります。

| やること | 工数 |
|----------|------|
| メインプロセスのヒープをプロファイル | 中 |
| 不要なモジュールの遅延化・除去をパッチ | 中〜大 |

**得られるもの**: 最大 100 MB 程度と推測。**ただし根拠は薄く、上流の設計次第**です。
時間を区切って（例: 1 日）調べ、成果が出なければ打ち切るべき性質の作業です。

---

### 提案 E: メインプロセスをネイティブに置き換える 🔴 高コスト・効果最大

Bun + デスクトップシェル（274 MB）を Rust（Tauri）や薄いネイティブシェル（約 20 MB）に
置き換えます。

```
現状               636 MB
メイン置き換え後   約 380〜400 MB（推定）
Obsidian           424 MB
```

**Obsidian をわずかに下回る程度**です。システム WebView の 363 MB は Tauri でも同じ
（Windows では同じものを使うため）なので、これが下限になります。

| 失うもの |
|----------|
| SQLite・MCP サーバー / クライアント・エージェントループ・ファイル監視の再実装（約 1 万行） |
| 「1 言語で完結」という現在の単純さ |
| Bun の組み込み SQLite と TS 直接実行 |

**推奨しません。** 理由は次節。

---

### 提案 F: WebView をやめる 🔴 最大コスト

ネイティブ UI（WinUI / Win32）にすれば合計 150 MB 程度になりますが、
クロスプラットフォーム性と現在の UI 全体を失います。**推奨しません。**

---

## 4. 私の推奨

**やるべき**: 提案 A（ヘッドレス）+ 提案 C（GC 実験）を今すぐ。
提案 B はスケール対応として、数値と無関係に必要です。

**時間を区切って調べる**: 提案 D。

**やるべきでない**: 提案 E・F。

### なぜ E を推奨しないか

1. **得られるのは同着**です。1 万行を書き直して Obsidian の 424 MB を
   380〜400 MB に、つまり 1.5 倍重い → 0.95 倍にするだけです。
2. **システム WebView の 363 MB は動きません。** 最大の項目が固定されている以上、
   何をしても劇的な改善にはなりません。
3. **本プロジェクトの差別化はメモリではありません。** ディスク 3.2 倍小、
   エージェント連携が最初から組み込み、OKF/LLM Wiki 準拠 — ここが価値です。
   400〜600 MB の差を現代のマシンで体感する場面は限られます。

メモリ効率を製品要件の第一位に置くなら E が唯一の道ですが、
その場合は**そもそも WebView を使う設計を選ばない**べきでした。

---

## 5. 付随して見つかった問題（軽量化とは別件）

当時のデスクトップシェルは WebView を **`--disable-web-security` 付き**で生成していました。

```
--disable-web-security
--allow-insecure-localhost
```

このフラグはネイティブ DLL（`libNativeWrapper.dll`）に埋め込まれており、
TypeScript 側からは無効化できません。

**現状の緩和**: 本アプリの CSP は `default-src 'none'; script-src 'self'` で、
外部オリジンへの接続とインラインスクリプトを禁止しています。ノート本文は
許可リスト方式でサニタイズしています。したがって**現実的な攻撃経路は塞がれています**が、
同一オリジンポリシーが無効という前提は、依存を追加する際に留意が必要です。

**対応案**: 上流に issue を上げるか、DLL にパッチを当てるか、
CSP を唯一の防壁として明示的に文書化するか。
軽量化とは独立した判断です。
