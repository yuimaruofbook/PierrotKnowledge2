## 2. 計測方法

### プロセスツリー全体を測る

両アプリともマルチプロセスです。

- **Obsidian** は Electron — メイン + レンダラ + GPU + ユーティリティ
- **PierrotKnowledge2**（当時のデスクトップ版）は OS の WebView を使うため
  `msedgewebview2.exe` の子が立つ。現行の `ui` モードにこの子プロセスはありません

**起動したプロセスだけを測ると、子プロセスに仕事を追い出しているアプリが
有利に見えます。** この比較ではそれは本アプリのほうなので、
親から辿れる子孫を全て合算しています（`scripts/bench/measure.ps1`）。

### 指標を 2 つ出す

| 指標 | 意味 |
|------|------|
| ワーキングセット | 実際に物理メモリに載っている量。**実使用に近い** |
| プライベートバイト | コミット済みで他プロセスと共有しない量 |

Bun（JavaScriptCore）はアドレス空間を大きく予約するため、
**プライベートバイトは実態を過大に見せます** — 素の Bun は常駐 46 MB に対し
232 MB をコミットします。判断にはワーキングセットを使ってください。

### コーパス

`scripts/bench/make-corpus.ts` が 300 ノートを生成します。

- frontmatter（`type` / `title` / `description` / `tags`）
- 日本語 6 段落 + 見出し + 番号付きリスト
- 各ノートから 3 本のウィキリンク（実際のリンクグラフができる）
- 12 サブディレクトリに分散、合計 1.3 MB

同じバイト列を Obsidian の Vault ルートと OKF バンドルの `wiki/` に置きます。
**両アプリが同じ内容を索引する**ことが前提です。

## 4. ヘッドレスの実運用計測

上記はいずれもアイドル状態の数値です。**エージェントが実際に働いているときの
消費**を測るため、MCP サーバーに現実的な負荷をかけました。

### ワークロード

`scripts/bench/workload.ts` が `AGENTS.md` の指示順どおりに 1 サイクルを回します。

```
read_agents_md → loop_start → skill_find → skill_open
  → retrieve ×5 / search ×5    （取得は最も重い経路）
  → list_concepts → unresolved_links → read_file
  → create_concept             （ノートが実際に増える）
  → loop_end
  5 サイクルごとに rebuild_index
```

400 ms ごとにワーキングセットをサンプリングし、負荷後 8 秒アイドルさせて
**戻るかどうか**も見ます。

### 結果（1,921 ツール呼び出し / 10.1 秒）

| 指標 | コンパイル済 | `bun run` |
|------|------------:|----------:|
| 起動直後 | 112.6 MB | 116.9 MB |
| 負荷中の平均 | 138.7 MB | 133.5 MB |
| 負荷中のピーク | 160.1 MB | 158.3 MB |
| **アイドル復帰後** | **129.0 MB** | 128.9 MB |
| スループット | 189.6 呼び出し/秒 | 180.6 呼び出し/秒 |

コンパイル済みと `bun run` にメモリの差はありません。
**コンパイルの利点は起動時間と、Bun のインストールが不要になること**です。

### 長時間走行（5,761 呼び出し / 32.6 秒）

| 指標 | 値 |
|------|---:|
| 起動直後 | 119.9 MB |
| 負荷中の平均 | 159.0 MB |
| ピーク | 179.5 MB |
| アイドル復帰後 | 136.7 MB |

100 → 300 サイクルで、アイドル復帰値は 129 → 137 MB。

> **注意**: このワークロードは毎サイクル `create_concept` を呼ぶため、走行中に
> コーパスが 300 → 600 ノートへ倍増しています。**増加分 8 MB の大半は実データ**で、
> リークとは切り分けられていません。コーパスを増やさない読み取り専用ワークロードでの
> 再測が必要です。

### 起動時間

```
ヘッドレス起動 → 最初の MCP 応答: 372 ms（3 回: 589 / 355 / 372）
デスクトップ版 → ウィンドウ表示:  710 ms
```

MCP ホストはサーバーを頻繁に spawn するため、この値は体感に直結します。

## 5. メモリの内訳

### ノート数はほぼ効かない

| 状態 | ワーキングセット |
|------|----------------:|
| バンドル未オープン | 559.7 MB |
| 300 ノート読み込み後 | 607.0 MB |
| **増分** | **+47.3 MB** |

**空の状態で既に 560 MB です。** コストはコーパスではなく土台にあります。

### 全額の帰属

同じ `Workspace` のコードを、デスクトップシェルも WebView も通さず、MCP スタンドアロンとして
起動して切り分けました。

```
bun run src/bun/mcp/standalone.ts（300 ノート） →  WS 107.4 MB
素の Bun ランタイム                              →  WS  46.4 MB
                                                    ────────────
当アプリのロジック + SQLite 索引                  →      61.0 MB
```

| 構成要素 | WS | 割合 | 所有者 |
|----------|---:|-----:|--------|
| システム WebView（5 プロセス） | 363 MB | 57% | Microsoft |
| デスクトップシェルのメイン上乗せ | 167 MB | 26% | シェル |
| Bun ランタイムの下限 | 46 MB | 7% | Bun |
| **当アプリのコード + 索引 + 300 ノート** | **61 MB** | **10%** | **私たち** |

**メモリの 90% は当プロジェクトのコードではありません。**

### システム WebView のチューニングは効かない

`WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS` で引数を渡して計測しました。

| 設定 | プロセス数 | 合計 WS | gpu-process |
|------|----------:|--------:|------------:|
| なし（基準） | 7 | 622.7 MB | 88.3 MB |
| `--disable-gpu` | 7 | 580.4 MB | 88.5 MB |
| `--in-process-gpu` | 7 | 612.7 MB | 88.3 MB |

引数が実際に届いていることは WebView のコマンドラインで確認済みです。それでも
**gpu-process は消えず、プロセス数も変わりません。** 合計 WS の揺れはメインプロセスの
GC タイミングによるもので、フラグの効果ではありません。

> **結論**: システム WebView のプロセスモデルはホスト側から制御できません。
> 削減案の検討は [軽量化の提案](ja/lightweight-proposal.md) を参照してください。

## 6. 何が言えて、何が言えないか

### 言えること

- ディスク占有は Obsidian の **1/3〜1/4**
- デスクトップ版の常駐メモリは **1.4 倍大きい**
- **ヘッドレスなら Obsidian の 1/3**
- 起動はいずれも 1 秒未満で、差は体感しにくい
- 300 ノート規模では、メモリは**ほぼ全てが土台のコスト**
- ヘッドレスは負荷をかけても 160 MB を超えず、アイドルで戻る

### 言えないこと

- **数万ノートでの挙動。** 300 ノートまでしか測っていません。
  傾き（1 ノートあたりのコスト）が両アプリで同じとは限りません
- **長時間のリーク。** 定常状態を数十秒で測っており、数時間後は見ていません
- **macOS / Linux。** WebView の実装が違うため、この結果は Windows 限定です
- **機能あたりの効率。** Obsidian はグラフビュー・Canvas・プラグイン機構を
  持ったうえでこの数字です。**同じ土俵ではありません**

## 7. 再現手順

```powershell
# 1. デスクトップ版 対 Obsidian（3 試行）
powershell -ExecutionPolicy Bypass -File scripts\bench\trials.ps1 -Trials 3 -Settle 25
```

```bash
# 2. ヘッドレスの実運用計測
bun run build:headless
bun run scripts/bench/make-corpus.ts /tmp/bench/wiki 300
bun run bench:workload /tmp/bench 100 --exe build/headless/okf-mcp.exe
```

| スクリプト | 役割 |
|-----------|------|
| `scripts/bench/make-corpus.ts` | 同一コーパスの生成 |
| `scripts/bench/measure.ps1` | プロセスツリー全体のメモリ集計 |
| `scripts/bench/trials.ps1` | 両アプリの起動・計測・**設定の復元** |
| `scripts/bench/workload.ts` | MCP に現実的な負荷をかけてサンプリング |

> `trials.ps1` は実在のユーザー環境の Obsidian を使います。設定
> （`obsidian.json` / `session.json`）は**バックアップして必ず復元**しますが、
> 実行中は Vault 一覧に一時的にベンチ用 Vault が登録されます。
